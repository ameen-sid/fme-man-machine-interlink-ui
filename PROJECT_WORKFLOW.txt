1. PROJECT OVERVIEW
================================================================================
Furukawa Minda Electric (FME) Man-Machine Interlink is a digital factory floor management application. It is built for shop floor operators, maintenance engineers, and quality assurance inspectors in automotive wire harness manufacturing plants. In traditional manufacturing setups, paper checksheets are filled by hand, leading to lost paperwork, unverified handwriting, delayed maintenance, and difficult audits. This application replaces those paper clipboards with responsive, digital checksheets for machine maintenance, quality inspection, poka-yoke (mistake-proofing) verification, 5S workplace audits, and breakdown logs. It also provides plant managers with a high-level operational telemetry dashboard to track hourly output production (HOP) and machine runtime hours across manufacturing shifts. The primary active plant modeled in the system is the Bawal Unit in Haryana, India, with expansion placeholders for the Gujrat Unit in Gujarat, India.

TECH STACK BREAKDOWN:
- JavaScript (ES Modules): The core programming language used to build application logic and reactive components.
- React 19 (v19.2.8): The component-based user interface library used to create declarative views and manage user interaction state.
- React DOM (v19.2.8): The React package that mounts the component tree into the web browser Document Object Model (DOM).
- React Router DOM (v7.18.4): The client-side routing library used to handle multi-level URLs, route parameters, and full-screen screen switches without page reloads.
- Vite (v8.3.0): The development server and production bundler that enables fast Hot Module Replacement (HMR) and bundles the project for release.
- Tailwind CSS (v3.4.19): The utility-first CSS framework used for fast, modern responsive styling and layout arrangement across all screen sizes.
- PostCSS (v8.5.28) & Autoprefixer (v10.6.1): Build-time CSS processing tools that inject browser compatibility prefixes into the compiled stylesheets.
- Lucide React (v1.46.0): A clean SVG icon library providing uniform industrial icons for machines, gauges, tools, cameras, and status indicators.
- Oxlint (v1.81.0): A high-speed Rust-based JavaScript and React linter that enforces code consistency and catches React Hook mistakes early.

3. HOW THE PROJECT STARTS
================================================================================
The execution life cycle from running the command to browser rendering occurs in six sequential steps:

STEP 1: DEVELOPER LAUNCHES VITE
- Command: `npm run dev`
- Tool: Vite reads `vite.config.js`. It starts a local HTTP development server (typically on `http://localhost:5173`) and compiles JSX on the fly using `@vitejs/plugin-react`.

STEP 2: BROWSER REQUESTS ROOT HTML
- The web browser loads `index.html`.
- The HTML loads fonts from Google Fonts (`Plus Jakarta Sans` and `JetBrains Mono`).
- It creates an empty DOM node: `<div id="root"></div>`.
- It executes the root entry script via `<script type="module" src="/src/main.jsx"></script>`.

STEP 3: REACT ROOT INITIALIZATION (`src/main.jsx`)
- The browser downloads and executes `src/main.jsx`.
- `main.jsx` imports `createRoot` from `react-dom/client` and imports the global styles in `src/index.css`.
- It mounts the root `<App />` component inside `<StrictMode>` into the DOM element with ID `root`.

STEP 4: AUTHENTICATION PROVIDER MOUNTING (`src/context/AuthContext.jsx`)
- `App.jsx` wraps the entire application with `<AuthProvider>`.
- The `AuthProvider` checks the browser's `sessionStorage` under the key `fme_operator_session`.
- If an active operator/quality session exists from an earlier login, it loads it into React state. Otherwise, it initializes as `null`.

STEP 5: ROUTER INITIALIZATION (`src/App.jsx`)
- `BrowserRouter` listens to the browser URL pathname.
- If the user visits the root `/`, the route rule `<Route index element={<Navigate to="/dashboard" replace />} />` redirects the browser directly to `/dashboard`.
- The parent wrapper component `MainLayout.jsx` is mounted.

STEP 6: MAIN LAYOUT RENDERING (`src/MainLayout.jsx`)
- `MainLayout` checks the current URL path.
- If the current route is NOT a full-screen checksheet (meaning the URL does not have 5 or more segments under `/machine-checksheet/`), `MainLayout` renders:
  1. The left-hand `<Sidebar />` with active route indicators and brand logo.
  2. The top `<Navbar />` with breadcrumb paths and user status indicator.
  3. The `<main>` container hosting the routed page via `<Outlet />`.
- If the current route is a specific checksheet (e.g. `/machine-checksheet/Bawal/CNC/C&C 01/Machine 5S checksheet`), `MainLayout` automatically hides both the Sidebar and Navbar so the operator receives maximum screen real estate for wide table entry.

FEATURE 1: VIEWING OPERATIONS TELEMETRY & HOURLY OUTPUT DASHBOARD
--------------------------------------------------------------------------------
User Goal: A plant manager wants to examine the output rate (units per hour) and active runtime hours of C&C Machine 01 over the past 15 days.

Trigger:
User opens the app or clicks "Dashboard" in the left sidebar.

Flow Diagram:
User clicks Dashboard -> Sidebar.jsx -> NavLink to /dashboard -> App.jsx -> OperationsDashboard.jsx -> Reads selected machine/process/days -> Computes period statistics -> Renders 3 custom dual-bar SVG/HTML charts

Step-by-step Execution:
1. React Router matches `/dashboard` and loads `src/dashboard/OperationsDashboard.jsx`.
2. The component initializes four cascading filter states:
   - Selected Unit: defaults to "Bawal".
   - Selected Operational Unit: defaults to "C&C".
   - Selected Process: defaults to "Auto Crimping".
   - Selected Machine: defaults to "C&C 01".
   - Selected Duration: defaults to 15 days (switchable to 7 or 30 days).
3. The component uses `useMemo` hooks to generate deterministic data:
   - Computes base HOP (Hourly Output Production) around 140-190 units/hr based on machine ID.
   - Generates daily runtime hours (0 to 15 hours/day) and daily unit output.
   - Computes period totals: Average HOP, Average Runtime, Total Output, and Uptime Percentage.
4. The user sees:
   - Top filter toolbar with 4 dropdowns and quick reset button.
   - Duration selector pills (7 Days, 15 Days, 30 Days).
   - Graph 1: Combined dual-bar graph showing two color-coded vertical bars for every single day (Green for HOP, Blue for Runtime) with hover tooltips.
   - Graph 2: Dedicated HOP trend bar chart with Min, Average, and Peak throughput badges.
   - Graph 3: Dedicated Runtime hours bar chart with peak indicator flags and uptime efficiency badge.

--------------------------------------------------------------------------------

Trigger:
User clicks the "C&C 01" machine card inside the Auto Crimping section.

Flow Diagram:
User clicks C&C 01 card -> c&cLayout.jsx -> requestAuth(machine) in AuthContext.jsx -> Checks activeSession -> If null, opens modal -> Operator enters OP Card No. + QI Card No. -> Clicks Authenticate -> Session saved to sessionStorage -> Callback executes navigate() -> /machine-checksheet/Bawal/CNC/C&C 01 -> MachineDetailPage.jsx -> OperationalChecksheets.jsx

   `navigate('/machine-checksheet/Bawal/CNC/C&C 01')`.
9. `MachineDetailPage.jsx` reads the URL, normalizes the machine ID, queries `getMachineModel(1)` from `src/utils/machineModels.js`, determining the model is `Alpha_355`.
10. `MachineDetailPage.jsx` renders `OperationalChecksheets.jsx`, showing the 9 available checksheets for Auto Crimping machines.

5. DEEP EXPLANATION OF EACH PART
================================================================================

MODULE 1: ENTRY & ROUTING
--------------------------------------------------------------------------------
FILE: `src/main.jsx`
- Purpose: The gateway of the React application.
- How it works: Imports `createRoot` and injects `<App />` into the `index.html` div with id `root`.
- Analogous to: The front door of a factory where all visitors must enter.
- Key code: `createRoot(document.getElementById('root')).render(...)`.

FILE: `src/App.jsx`
- Purpose: The central traffic controller and route map.
- How it works: Defines all client-side URL routes using React Router DOM. It maps URLs like `/dashboard`, `/machine-checksheet/:unit`, and nested checksheet paths to their respective page components.

6. DATA AND DATABASE (STORAGE ARCHITECTURE)
================================================================================
The application is currently designed as a client-side web application with local browser persistence. There is no external relational database (like PostgreSQL or MySQL) or NoSQL database connected in this code.

Data persistence is managed across three distinct storage mechanisms:

1. COMPONENT MEMORY (REACT `useState`)
   - Transient data entered into table cells, daily shifts, and telemetry numbers are held in React component state.
   - Lifetime: Exists while the component remains mounted.

2. BROWSER `sessionStorage` (USER SESSION STATE)
   - Storage Key: `fme_operator_session`
   - Shape:
     {
       "operatorCardNo": "OP-84210",
       "inspectorCardNo": "QI-39145"
     }
   - Lifetime: Persists while the browser tab remains open. Closing the browser tab automatically logs out the operator.

3. BROWSER `localStorage` (CHECKSHEET RECORDS & UPLOADED PHOTOS)
   Multiple checksheets automatically serialize form entries into `localStorage` as JSON strings:
   - Observation Checksheet:
     Key: `fme_observation_pm_<machineName>`
     Data: `{ machineName, serialNo, rows: [...], updatedAt }`
   - Micrometer Guide Custom Photos:
     Key: `fme_instrument_center_photo_<machineKey>_<type>`
     Data: Compressed Base64 JPEG data URL
   - Manual Crimping Inspection Report:
     Keys: `mcr_inspection_report_<machineKey>_header`, `..._records`, `..._abnormality`
   - Manual Crimping Instrument Checksheet:
     Keys: `mcr_instrument_checksheet_<machineKey>_point_meta`, `..._point_grid`, etc.
   - Manual Crimping PM Checksheet:
     Keys: `mcr_pm_checksheet_<machineName>_header`, `..._cells`, `..._footer`
   - Mecal-05 Daily Checksheet:
     Keys: `mecal05_daily_checksheet_<machineName>_header`, `..._grid`, `..._obs`
   - Manual Crimping Poka-Yoke:
     Keys: `mcr_pokayoke_<machineName>_header`, `..._machines`, `..._grid`, `..._photo`
   - Manual Crimping Predictive Maintenance:
     Keys: `mcr_predictive_<machineName>_header`, `..._points`, `..._grid`, `..._footer`
   - Resistance Welding Checksheets:
     * Daily: `rw_daily_<machineName>_meta`, `..._op_grid`, `..._mt_grid`, etc.
     * 5S: `fme_rw_5s_<machineName>_meta`, `..._grid`, `..._photos`, etc.
     * Inspection: `rw_inspection_report_<machineKey>_meta`, `..._blocks`
     * Instrument: `rw_instrument_checksheet_<machineKey>_blade_grid`, `..._scale_grid`
     * Machine PM: `rw_pm_checksheet_<machineKey>_header`, `..._cells`, `rw_pm_photos_<machineKey>`
     * Predictive Maintenance: `rw_predictive_<machineName>_meta`, `..._grid`, `..._footer`

Data Movement Flow:
User edits input -> React onChange handler updates state -> Auto-save effect or Save button triggers `localStorage.setItem(key, JSON.stringify(data))` -> When page reloads, initial state initializer reads `localStorage.getItem(key)` and deserializes with `JSON.parse()`.

   Open a terminal in the project root directory and run:
   ```bash

   ```
   This downloads all packages listed in `package.json` into the `node_modules/` folder.

   ```bash
   npm run dev
   ```
   Output will display the local development URL, usually:
   `http://localhost:5173/`
   Open this URL in Google Chrome or Microsoft Edge.

3. RUN CODE LINTER:
   ```bash
   npm run lint
   ```
   Runs Oxlint to check for syntax errors or invalid React Hook usage.

4. BUILD PRODUCTION ARTIFACTS:
   ```bash
   npm run build
   ```
   Vite compiles and minifies all JavaScript, SVG, and CSS into static distribution files inside the `dist/` directory.

5. PREVIEW THE PRODUCTION BUILD LOCALLY:
   ```bash
   npm run preview
   ```
   Starts a lightweight local web server serving the `dist/` production bundle to test performance before deploying.

6. DEPLOY TO PRODUCTION WEB SERVER:
   Because this is a pure client-side Single Page Application (SPA), the contents of the `dist/` folder can be copied to any static web host, such as:
   - Nginx or Apache HTTP Server
   - AWS S3 + CloudFront
   - Vercel or Netlify
   - Internal factory on-premises web server
   CRITICAL SERVER CONFIGURATION: The web server must have URL rewriting enabled (fallback to `index.html` for all non-file routes) so that deep URLs like `/machine-checksheet/Bawal/CNC/C&C 01` do not trigger HTTP 404 errors.

10. COMMON PROBLEMS AND FIXES
================================================================================

PROBLEM 1: 404 NOT FOUND ON BROWSER REFRESH WHEN VIEWING A CHECKSHEET
- Cause: React Router handles routing in the browser. When the page is reloaded at a deep URL like `/machine-checksheet/Bawal/CNC/C&C 01/Machine 5S checksheet`, a static web server without rewrite rules searches for a literal folder or file matching that path and fails.
- Fix: Configure the production web server (Nginx/Apache) to redirect all unknown routes to `index.html`. In development mode, Vite handles this automatically.

PROBLEM 2: BROWSER FAILS TO SAVE CHECKSHEET PHOTO (STORAGE QUOTA ERROR)
- Cause: Uploading very large raw smartphone camera images (5 MB to 10 MB) directly into `localStorage` exceeds the browser quota limit (usually ~5 MB per domain).
- Fix: The component `MicrometerComponentGuide.jsx` already includes a Canvas-based compression helper (`compressImage`) scaling images down to 1200px max dimensions and 0.85 JPEG quality before storing. Make sure other image upload cells use similar compression.

PROBLEM 3: SESSION LOST AFTER CLOSING THE BROWSER TAB
- Cause: Operator login credentials are intentionally stored in `sessionStorage` (`fme_operator_session`), which clears itself when the tab is closed.
- Fix: This is a designed security feature for shared factory workstations. If persistence across days is desired, change `sessionStorage` in `src/context/AuthContext.jsx` to `localStorage`.

PROBLEM 4: MACHINE NUMBER 13 DOES NOT APPEAR IN AUTO CRIMPING
- Cause: In `AutoCrimpingView.jsx` and `OperationsDashboard.jsx`, the array generator explicitly excludes 13: `.filter((num) => num !== 13)`.
- Explanation: This matches real-world manufacturing plant floor numbering where machine number 13 was skipped due to facility naming conventions. It is intentional, not a bug.

11. GLOSSARY
================================================================================
- C&C: Cutting & Crimping. The automated wire manufacturing process where electrical cables are cut to exact length, stripped of insulation, and crimped onto metal terminal contacts.
- MMI: Man-Machine Interlink. The interface connecting human factory operators with industrial machinery protocols, checks, and logs.
- HOP: Hourly Output Production. The count of finished wire harness circuits manufactured per hour.
- POKA-YOKE: Japanese manufacturing term meaning "mistake-proofing". Automated sensors, cameras, or mechanical pins that prevent defective parts from advancing.
- 5S: Japanese workplace organization methodology consisting of five steps: Sort (Seiri), Set in order (Seiton), Shine (Seiso), Standardize (Seiketsu), and Sustain (Shitsuke).
- PM: Preventive Maintenance. Scheduled, routine service tasks (lubrication, inspection, calibration) performed to prevent unexpected equipment breakdown.
- CFM: Crimp Force Monitor. A piezoelectric sensor mounted on a crimping press measuring the exact mechanical pressure curve of every crimping stroke to detect missing wire strands.
- MCR: Manual Crimping Machine (specifically the Mecal-05 desktop electric bench press).
- R/SW: Resistance Welding machine. Joins wires or terminals using heat generated by electrical resistance.
- APPLICATOR: The heavy, precision interchangeable tooling die installed inside a crimping press to shape a specific terminal type.
- TERMINAL: The small metal connector crimped onto the end of an automotive wire to allow it to plug into a vehicle electrical connector block.

12. IDEAS FOR IMPROVEMENT
================================================================================
1. CONNECT A REAL BACKEND DATABASE
   Currently, all checksheets save locally to browser `localStorage`. If an operator switches to a different tablet or computer, their past records are not visible. Connecting a centralized Node.js/PostgreSQL or Python/FastAPI backend API would allow checksheet records to sync across the entire plant.

2. FINISH ASSEMBLY SECTION IMPLEMENTATION
   The 9 files under `src/machine-checksheets/units/assembly/allChecksheets/` (5sChecksheet, breakdownSummary, dailyChecksheet, inspectorReport, instrumentChecksheet, operatior&MachineSummary, pmChecksheet, PokayokeChecksheet, processProductionStatus) are currently 0-byte placeholders. They should be implemented with real assembly conveyor criteria matching the CNC standards.

3. DEDUPLICATE AUTO CRIMPING MODEL CHECKSHEETS
   Inside `src/machine-checksheets/units/c&c/autoCrimping/`, seven separate folders (`alpha355`, `g252`, `g253`, `g448`, `jam`, `trd301`, `trd411f`) contain nearly identical checksheets with minor string replacements. Refactoring these into unified shared checksheets that take `model` as a prop would eliminate over 20,000 lines of duplicate code.

4. IMPLEMENT LIVE MACHINE TELEMETRY WEBSOCKETS
   The dashboard metrics in `OperationsDashboard.jsx` and `AutoCrimpingView.jsx` currently use deterministic mathematical algorithms for simulation. Connecting the front-end to industrial IoT protocols (like MQTT or OPC-UA via WebSockets) would turn this into a live factory floor monitor.

5. EXPORT CHECKSHEETS TO EXCEL (XLSX / CSV)
   While `window.print()` allows printing paper and PDF copies, quality departments frequently require raw Excel records for statistical process control (SPC) and automotive ISO/TS audits. Adding an export to CSV or XLSX button on `ChecksheetHeaderNav.jsx` would greatly streamline quality reporting.
